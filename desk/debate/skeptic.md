# 懷疑者筆記｜2026-09-19

角色：懷疑者。過去 24 小時已出現的失敗模式：URL 清單當內容、AI 半成品、把簡報包裝成正式報導。使用者約五小時後回來。

## 直接攻擊的三類計畫

1. 發布 teasers（標題＋導語＋「目前僅見 XX」）  
   這不是 feature，也不是 culture。PROTOCOL 寫得很清楚：若只剩導語與來源提示，就只能放進 briefing。把 teaser 塞進 feature.md 或 culture.md，等於再次重演「把簡報賣成新聞」的失敗。讀者坐下後沒有多知道任何機制、數字性質或爭議邊界，只是多了一層包裝。

2. 依賴 Workers AI 當每日主產線  
   目前 Workers AI（含 Markdown Conversion 與 GLM 類模型）在長文與多源交叉核對上的穩定度不足。過去 24 小時已出現不完整 stub 與英文殘留。把它當成「一定能產出兩篇完整 2000 字文章」的前提，等於把整條日更綁在尚未驗證的黑箱上。Cron 或 /run 一旦逾時、配額觸頂、或轉換失敗，就只會再產出一堆半成品。

3. 承諾「250 來源」  
   GDELT 單次查詢上限是 250 筆記錄，那是容量，不是已核對的可用來源。把「有 250 筆」寫成「有 250 個可靠來源」是數字幻覺。真正能深讀並交叉核對的全文，每日能穩定處理的數量遠低於此。承諾 250 只會迫使系統用標題堆或 URL dump 充數，再次回到已失敗的模式。

## 若在單一 grokbot 執行中硬衝「兩篇完整 2000 字文章＋簡報」，07:30 明天會壞什麼

時間軸假設：現在約 03:08，使用者五小時後回來（約 08:00 前後）。若在今晚／凌晨用單一 run 硬衝兩篇各約 2000 字完整文章＋briefing：

- 全文抓取與轉換會先卡住或半途失敗。Workers AI Markdown Conversion 對付費牆、動態頁、長頁並不可靠；失敗後系統容易退回標題列表或「目前僅見」句式。
- 寫作階段會變成「先湊字數」。為了湊到 2000 字，模型會重複背景、堆疊未核對的次要細節，或把 briefing 項目硬拉長。結果不是完整文章，而是加長版 teaser。
- 交叉核對會被犧牲。真正可用的做法是先深讀 8–12 篇原文、記筆記、再寫；單一 run 沒有這個時間與注意力預算。07:30 左右若仍在跑，或已產出半成品，feed 與 editions 會再次出現「可發布但不應發布」的檔案。
- 使用者回來時看到的，極可能是：briefing 還能看、feature/culture 又變成昨天那種短而空的段落，或直接是 URL dump。這會再次觸發「失敗模式已確認」的判斷，而不是「產品可用」。

一句話：硬衝兩篇 2000 字完整文章，在現有工具與單一 run 約束下，會在明天早上把「誠實的簡報」再度污染成「假裝完整的報導」。

## 誠實的最低可行日更產品（MVP）

只承諾能穩定交付、且符合 PROTOCOL 與 ARTICLE_SPEC 的東西：

- **每日必出**：briefing.md  
  3–5 則，每則 200–400 字。有情境、有具名機構或數字、有來源對得上。不堆標題。

- **有材料才出**：feature.md 與 culture.md  
  各 0–1 篇完整文章（不是 teaser）。完整的定義以 ARTICLE_SPEC 為準：發生什麼、機制或場景、時間深度、數字性質、具名主體、爭議邊界、我們知道的極限。字數目標可訂 1200–2000，但「完整」優先於「湊到 2000」。若材料只夠寫成 briefing 項目，就不要硬寫成 feature。

- **不做的事**：  
  - 不把 Workers AI 當成唯一寫作引擎；人工深讀與筆記優先。  
  - 不承諾來源數量；只報告實際深讀並核對過的篇數。  
  - 不發布 teaser 當正式報導。  
  - 不在單一 grokbot run 裡同時衝兩篇長文＋簡報；先保 briefing，再決定是否有一篇夠完整的長文。

- **輸出節奏**：  
  先寫 notes.md（原文語言筆記＋核對來源），再寫 Traditional Chinese 正文。feed.xml 只在通過「非 dump、非 stub」檢查後才更新。

這才是能連續運作、且不會在 07:30 再次崩潰的日更下限。其他任何「兩篇完整長文保證出」「250 來源」「全自動 Workers AI」的說法，目前都是會重演失敗的計畫。
